# Linux-Native Virtualized Compute Cluster — Prototype

A working prototype implementation of the two-deliverable design described
in `Linux-Native_Virtualized_Compute_Cluster_Prototype.docx` and its
`Executive_Summary.docx`: replacing a VMware-based compute cluster with a
RHEL-native stack (KVM/libvirt, OVS/OVN, Ceph RBD) and automating it
end-to-end.

- **Deliverable A** (`bootstrap/`) — turns a fresh, STIG'd RHEL 9 server
  into a configured compute node.
- **Deliverable B** (`management/`) — a FastAPI service that provisions
  declarative "missions" (sets of VMs with networks, storage, GPU, and
  placement) across the cluster.
- **Rescue/setup tooling** (`rescue/`) — runs Deliverable A remotely,
  1-to-many, from a single external node against airgapped hosts. See
  "Deployment model" below.
- **Proof of concept** (`management/mission_defs/mission_alpha.yaml`) — the
  40-VM mission from the Executive Summary: 10 persistent linked-clone
  VMs + 30 diskless PXE VMs, 6 NICs each (240 NICs total), 7 with GPU
  (MIG/vGPU) passthrough. `mission_bravo.yaml` is a 4-VM (2 linked-clone +
  2 PXE) quick-test version of the same conventions.

**See `CODE_REVIEW.md`** for a full architecture/assumptions review,
deployment readiness checklist, and air-gap-specific recommendations —
read that before a real deployment, not just this file.

**See `diagrams/00-README.md`** for a full set of architecture diagrams
(Mermaid format) — high-level lifecycle diagrams for each deliverable and
combined, plus low-level component, sequence, networking, storage, GPU,
state-machine, topology, and data-model diagrams, with a suggested
reading order for a guided deep dive.

## Read this first: MAC addresses are an operator input, not generated

**Per operator confirmation, the guest software running inside mission
VMs has MAC addresses hardcoded into its licensing/configuration.** This
system therefore never invents the *identifying* part of a real
deployment's MAC addresses — every VM interface's `mac_suffix` (the last
three octets) in a mission YAML is normally an explicit, operator-supplied
value, used exactly as written, every time that mission is deployed.

What the system *does* generate automatically is the **first three
octets** — a fresh, random, collision-checked prefix for each individual
*deployment* of a mission, so the exact same mission file can be deployed
more than once concurrently, fully isolated at the MAC layer, while every
deployment's configured suffixes (and any substring-matching tooling
relying on them) stay identical:

```
deployment 1 of Mission-Alpha:  AA:BB:CC:10:00:00   (random prefix + your configured suffix)
deployment 2 of Mission-Alpha:  XX:YY:ZZ:10:00:00   (different random prefix, same suffix)
```

`mission_alpha.yaml` and `mission_bravo.yaml` have every interface's
`mac_suffix` filled in already, but they are **arbitrary placeholders**
generated by `tools/generate_mission.py` purely so the files are complete
and ready to exercise end-to-end. **Replace them with your actual
required values before deploying against real hardware or licensed
images.** Full schema/rationale: `management/mission_defs/README.md`.
Implementation: `management/core/macs.py`.

`core/` (inside `management/`) is worth calling out specifically: it's
where almost all of the actually-interesting logic lives (MAC/prefix
resolution, GPU-profile-aware placement validation, libvirt XML
rendering, mission state machine), deliberately factored out with **zero
dependency on fastapi, pydantic, or any infrastructure client library** —
see the next section for why.

## Architecture: why `management/core/` exists

The design doc specifies Pydantic models and a FastAPI app for the
management service. This build environment has **no network egress**, so
`fastapi`, `pydantic`, `ovsdbapp`, `python3-libvirt`, `python3-rados`, and
`python3-rbd` could not be installed or exercised here (see "What was and
wasn't executed," below).

Rather than leave the hardest, most bespoke logic in this project
untested, it's factored into `management/core/` as plain dataclasses and
pure functions with only the standard library, PyYAML, and Jinja2, all of
which *are* available here. `management/api/models.py` defines the
Pydantic schemas the design doc calls for and converts to/from these
dataclasses at the API boundary, so a real deployment (with
`requirements.txt` installed) behaves exactly as specified, while every
non-trivial algorithm underneath it — MAC/prefix handling, GPU-profile
capacity/placement validation, libvirt XML generation, golden-image
revision resolution, mission state transitions — is unit-tested right
now, in this repository, without any of those packages.

`management/clients/*.py` (libvirt/OVN/Ceph/NetworkManager wrappers) use
guarded imports (`try: import libvirt / except ImportError: libvirt =
None`) so the codebase imports cleanly even where those packages aren't
present, and raise one clear, actionable error if you call into them
without the real library installed. On a bootstrapped RHEL host, they're
installed by `bootstrap/modules/packages.py` and this guard never
triggers.

## API and versioning

Interactive documentation is auto-generated by FastAPI at `/docs`
(Swagger UI) and `/redoc` once the service is running — every endpoint's
docstring and every field description below appears there automatically.
This section is a plain-text summary for offline/airgapped review without
a running server.

| Method | Path | Body | Behavior |
|---|---|---|---|
| `POST` | `/missions` | `MissionDefinition` | Validate placement + atomically resolve this deployment's MAC prefix/addresses and GPU device allocations, register it, and kick off provisioning in the background. Returns `202` with `{mission_id, mac_prefix}`; `422` if malformed/infeasible, `409` if a well-formed mission currently can't get a MAC prefix or GPU slice because other active deployments hold them all. |
| `GET` | `/missions/{id}` | — | One mission deployment's current state, step-by-step audit log, and error (if any). |
| `DELETE` | `/missions/{id}` | — | Tear down VMs, then OVN networking, then runtime storage, in the background. Returns `202`. |
| `GET` | `/missions` | — | Every tracked mission deployment, any state. |
| `GET` | `/hosts` | — | Host inventory summary: CPU/memory capacity + available GPU profile slice counts. |
| `GET` | `/health` | — | Lightweight liveness check: the service is up and its config loads. Does **not** touch any host, OVN, or Ceph. |
| `GET` | `/cluster/health` | — | Full, live infrastructure scan: opens a connection to every host, checks OVN and Ceph, rolls up every mission by state. Simple pass/fail (`ok: bool`) plus detailed per-host/service status. |

**Deployment workflow**: `POST /missions` → poll `GET /missions/{id}`
until `state == "Running"` (or `"Error"`, with `error` set and `steps`
showing which stage failed) → optionally re-check acceptance criteria any
time with `tools/validate_deployment.py --mission-id <id>` → `DELETE
/missions/{id}` when done, poll until `state == "Destroyed"`.

**Versioning**: `api/routes.py`'s `API_VERSION` constant is surfaced on
every response via the `X-API-Version` header and in `GET /health`'s
underlying app metadata. It's bumped on any backward-incompatible
schema/behavior change — e.g. this project went from `1.0.0` to `1.1.0`
when the MAC scheme moved from a flat `macs:` block to per-interface
`mac_suffix` and GPU moved from `gpu: bool` to `gpu: {profile}`. This is a
lightweight, in-process convention rather than URL path versioning
(`/v1/missions`) — appropriate for this prototype's current
single-consumer scope; revisit if/when there are multiple API consumers
that need to move to a new schema independently of each other.

## Deployment model

Two genuinely different operational phases, using this repo two different ways:

**Phase 1 — initial host bootstrap (Deliverable A), from an external
rescue/setup node.** Target hosts are freshly-STIG'd RHEL images with no
initial setup, reachable only from a dedicated rescue node on the
management network (themselves airgapped from the wider internet).
`bootstrap.py` itself only ever configures the one host it's invoked on;
`rescue/orchestrate.py` is what turns that into a 1-to-many operation —
it rsyncs `bootstrap/` + `config/` to each target host and runs
`bootstrap.py` there over SSH, capturing every host's output centrally
under `rescue/logs/` in addition to that host's own local logging. See
`rescue/README.md` for the exact STIG'd-host prerequisites (SSH/sudo
access, `python3`, `rsync`, SELinux/firewalld implications) and for
getting packages onto hosts with zero internet access at all
(`bootstrap/scripts/fetch_offline_packages.sh` +
`bootstrap/scripts/setup_local_repo.sh`).

**Phase 2 — the management service (Deliverable B), running
persistently within the cluster.** Once every host is bootstrapped, the
management API needs to run somewhere *inside* the cluster long-term (not
from the rescue node, which has no ongoing role once bootstrap is done).
Pick one host (or a dedicated management node, for a real deployment) and
install `management/mission-management.service` there:

```bash
# On the chosen host, as part of setting it up to run the management service:
cd /opt/mission-compute-cluster/management
python3 -m venv .venv && .venv/bin/pip install -r ../requirements.txt
sudo useradd -r -G libvirt mission-mgmt   # dedicated, unprivileged service account
sudo cp mission-management.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now mission-management.service
```

See `management/mission-management.service`'s own comments for the
account/hardening reasoning. That unit also sets `MISSION_DB_PATH`, so
mission state (including in-flight deployments) survives a restart of
this service -- on startup, before accepting any requests, it also
reconciles that recovered state against what's actually running live on
the cluster (see "Design choices and deviations" below and
`services/reconciliation.py`). This is still a prototype — the design doc
explicitly scopes high-availability of the management service itself as
future work, so this is a single systemd unit on a single host with a
local SQLite file, not a clustered/HA deployment with a shared database.

## What was and wasn't executed in this build environment

This project was built with no network access and none of
qemu-kvm/libvirt/OVS/OVN/Ceph/RHEL available — only Python 3.12, PyYAML,
and Jinja2. Here's exactly what that did and didn't allow, current as of
the schema redesign covering per-deployment MAC prefixes, MIG/vGPU GPU
profiles, and separated golden/runtime storage.

**Executed and verified here, with real output shown during development:**
- `bootstrap.py`'s full orchestration in `--dry-run` mode against the new
  consolidated `config/`, and its `--check-only` validation path.
- 15 unit tests for `bootstrap/modules/*`.
- 14 unit tests for `rescue/orchestrate.py`'s command construction and
  multi-host orchestration logic (rsync/SSH commands themselves mocked —
  no real SSH target in this sandbox).
- 211 unit/pipeline tests for `management/`, including:
  - Every domain-model validation rule in `core/types.py`, including
    per-interface `mac_suffix` format/uniqueness rules.
  - `core/macs.py`'s prefix-per-deployment resolution: locally-
    administered-bit-pattern prefix generation, prefix collision
    avoidance against other active deployments, and — directly
    exercising the operator's own worked example — that two concurrent
    deployments of the identical mission get different prefixes but
    identical configured suffixes.
  - `core/placement.py`'s GPU-profile-aware capacity validation (a MIG/
    vGPU profile name, not just a GPU count), its reference bin-packer,
    and `reserve_gpu_devices`'s atomic, cross-deployment device
    reservation -- including a regression test that reproduces the exact
    bug this project caught in its own review: two independent missions,
    each individually valid against total host capacity, correctly
    conflict (`409`, not a silent double-allocation) when only one
    physical GPU slice actually exists between them.
  - `core/xml_render.py` rendering real libvirt domain XML for every VM
    shape (linked-clone, PXE, mdev-based GPU passthrough, both storage
    backends, and VM interface counts from 1 up to 8+ -- there is no
    fixed NIC count anywhere in this pipeline) and parsing it back with
    `xml.etree.ElementTree` to confirm exact NIC count, MAC values, disk
    presence/absence, GPU `<hostdev type='mdev'>` presence/absence,
    CPU/memory, and the embedded `<metadata>` block used by
    `services/reconciliation.py` to trace a live VM back to its mission.
  - `core/serialization.py`'s MissionSpec/MissionStatus <-> JSON
    round-tripping (every field, including nested VMs/interfaces),
    confirming the output is genuinely `json.dumps`-safe.
  - `core/state.py`'s SQLite persistence path specifically (opt-in via
    `MISSION_DB_PATH`; the default remains in-memory-only with zero
    import-time side effects) -- using real temp-file databases to
    confirm a mission's full state (including its MAC prefix and GPU
    allocations) survives a MissionStore being discarded and a new one
    constructed against the same file, simulating a process restart.
  - `services/reconciliation.py`'s drift detection: a mission confirmed
    intact, a mission missing some or all of its VMs after a restart, and
    a mission discovered running live with no database record at all
    (correctly reconstructed on a best-effort basis, and correctly
    freeing its GPU/MAC reservations once later destroyed) -- with
    `clients/libvirt_client.py` mocked out but exercised against real
    rendered domain XML (via `core/xml_render.py`), not hand-written XML
    fixtures.
  - `services/storage.py`'s golden-image catalog resolution (by name +
    revision) and its dispatch to the right cross-pool-clone /
    cross-cluster-copy / mount-copy path per `config/storage.yaml`'s
    `golden.source`, with `clients/ceph_client.py` mocked out.
  - `services/cluster_health.py`'s infrastructure scan rollup logic, with
    `clients/*` mocked out.
  - The full pipeline against the *actual* generated 40-VM
    (`mission_alpha.yaml`) and 4-VM (`mission_bravo.yaml`) mission files:
    parse → placement validation → MAC resolution → XML rendering for
    every VM, confirming total NIC/GPU counts, zero MAC duplicates, and
    that GPU VMs exactly fill the configured MIG/vGPU slice counts.
  - `workers/deploy.py` / `workers/teardown.py`'s orchestration control
    flow (step ordering, GPU mdev allocation by profile, error
    propagation, mission state transitions, MAC-prefix/GPU-allocation
    release on teardown) AND `workers/deploy.py`'s automatic rollback on
    failure -- including that a failed-then-rolled-back mission can be
    resubmitted immediately, and that a rollback which itself fails
    correctly holds resources reserved rather than freeing them
    prematurely -- with the services layer mocked out.
  - That `clients/*.py` import cleanly and fail with a clear, actionable
    error (not a crash) when the real libvirt/ovsdbapp/rados libraries
    aren't present.
  - A regression guard confirming the config duplication the operator
    flagged (`bootstrap/config/` + `management/inventory/`, and the
    separate `management/placement/` file) doesn't reappear.

**Written to spec but NOT executable here (no network, no real
infrastructure):**
- `management/api/*.py` (FastAPI routes and Pydantic models), including
  `api/app.py`'s startup `lifespan` handler that calls
  `services/reconciliation.py` — fastapi/pydantic aren't installable
  without network access. This code is a thin, well-trodden
  CRUD+background-task wrapper around the already-tested
  `core`/`services` logic (`reconciliation.py`'s own scan/comparison
  logic IS unit-tested, against real rendered domain XML, with only
  `clients/libvirt_client.py`'s connection mocked out); the risk surface
  this layer adds is low, but it has not been run.
- Any real call into `clients/libvirt_client.py`, `clients/ovn_client.py`,
  or `clients/ceph_client.py` — these need a real hypervisor, a real OVN
  Northbound DB, and a real Ceph cluster respectively. `ovn_client.py`'s
  `connect()` in particular follows the standard `ovsdbapp` IDL-connection
  pattern but its exact constructor signature has shifted across
  `ovsdbapp` releases — validate it against the pinned version in
  `requirements.txt` before relying on it. `clients/ceph_client.py`'s
  cross-cluster (`ceph_rbd_remote`) and mount-based golden-image copy
  paths shell out to the `rbd`/`qemu-img` CLIs (see that file's module
  docstring for why) and are correspondingly less exercised than the
  librados/librbd-native path — validate these first against real Ceph.
- `rescue/orchestrate.py`'s actual `rsync`/`ssh` execution (the command
  construction and orchestration control flow ARE tested — see above —
  but no real remote host exists in this sandbox to run them against).
- The shell scripts under `bootstrap/scripts/` and
  `bootstrap/tests/test_bootstrap.sh` — these are written for and must
  run on a real (or freshly kickstarted) RHEL host.
- GPU MIG/vGPU slice creation itself (`nvidia-smi mig -cgi ...` / the
  NVIDIA vGPU Manager), PXE network boot, live migration, and STIG
  compliance scoring — all inherently require real hardware.

If you want to verify any of the "written to spec" pieces yourself: `pip
install -r requirements.txt` in a networked environment, then `pytest
management/tests` (all tests are plain `unittest.TestCase`s and run under
pytest too) plus `uvicorn api.app:app --reload` from `management/` to
bring up the API against your own inventory.

## Prerequisites (real deployment)

- RHEL 9 hosts with VT-d/AMD-Vi enabled in BIOS for any host running GPU
  VMs, and MIG (H100) / vGPU (L4) slices already created on those hosts —
  see `bootstrap/scripts/enumerate_mdev_gpus.sh`'s header comment for
  pointers, since slice creation itself is a manual, driver-specific step
  this automation doesn't perform.
- A Ceph cluster reachable from every compute host for the `runtime` pool
  (or set `storage_backend: local_qcow2` per host in `config/hosts.yaml`
  to use the qcow2-backing-file fallback instead), and a separate golden-
  image source per `config/storage.yaml`'s `golden.source` (same cluster
  different pool, a remote cluster, or a filesystem mount).
- A place to run `ovn-northd` and the OVN Northbound/Southbound DBs
  (`config/hosts.yaml`'s `ovn_central` — one of the compute hosts works
  for a prototype).
- If airgapped: see `rescue/README.md`'s "Getting packages onto airgapped
  hosts" section before running bootstrap.

## Quickstart

```bash
# 1. Bootstrap every host -- from an external rescue/setup node, remotely:
./rescue/orchestrate.py --all --dry-run     # rehearse first
./rescue/orchestrate.py --all                # then for real
# (or locally, one host at a time, if you're not using the rescue-node model:
#  sudo ./bootstrap/bootstrap.py --host compute01)

# 2. Install the management service's dependencies (in a venv, on the
#    host that will run it persistently -- see "Deployment model")
cd management
python3 -m venv venv && source venv/bin/activate
pip install -r ../requirements.txt

# 3. Review management/mission_defs/mission_alpha.yaml -- especially every
#    interface's mac_suffix (see the callout at the top of this README) --
#    then start the API (or install management/mission-management.service
#    for a persistent deployment)
uvicorn api.app:app --host 0.0.0.0 --port 8000

# 4. Submit the mission
curl -X POST http://localhost:8000/missions \
    -H 'Content-Type: application/json' \
    -d @mission_defs/mission_alpha.yaml   # or convert to JSON first

# 5. Poll status
curl http://localhost:8000/missions/<mission_id>

# 6. Check overall cluster health any time
curl http://localhost:8000/cluster/health

# 7. Re-check this mission's acceptance criteria any time later
python3 ../tools/validate_deployment.py --mission-id <mission_id>

# 8. Tear down
curl -X DELETE http://localhost:8000/missions/<mission_id>
```

To regenerate `mission_alpha.yaml` / `mission_bravo.yaml` (e.g. after
changing `config/hosts.yaml`'s capacity):
```bash
python3 tools/generate_mission.py           # mission_alpha.yaml
python3 tools/generate_mission.py --small   # + mission_bravo.yaml
```
This rewrites the `vms:`/`placement:`/`interfaces:` sections from
scratch — re-apply any manual `mac_suffix` edits you'd made afterward.

## Design choices and deviations worth knowing about

- **MAC scheme**: see the callout at the top of this README and
  `management/mission_defs/README.md` — this is the single most
  significant deviation from a literal reading of the source docs' own
  MAC examples, driven directly by operator feedback.
- **GPU passthrough is mdev-profile-based, not raw PCI**: the source
  docs' own examples show whole-PCI-device passthrough; the operator's
  actual GPUs (H100 MIG, L4 vGPU) need profile-specific mediated-device
  passthrough instead. See `management/mission_defs/README.md`'s "GPU
  profiles" section.
- **GPU host capacity**: the source doc's own illustrative host table
  only has 4 total GPU slots (2+2 across 4 hosts) — not enough for the
  scenario's 7 GPU VMs. `config/hosts.yaml` gives compute01 4x H100 MIG
  slices and compute03 4x L4 vGPU slices. Confirm actual profile
  names/counts/UUIDs against your real hardware.
- **Golden images are a separate store from runtime disks**: per operator
  requirement, so runtime VMs can live on local Ceph RBD while golden
  images come from a remote cluster or a plain mount. See
  `config/storage.yaml` and `clients/ceph_client.py`'s module docstring
  for the clone-vs-copy tradeoff this implies.
- **Single source of truth for cluster config**: `config/` replaced two
  previously-duplicated copies (`bootstrap/config/` +
  `management/inventory/`) and a separately-duplicated placement file
  (`management/placement/`) — all removed. `management/tests/test_config_loader.py`
  guards against this reappearing.
- **Every VM gets all 6 networks**: the Executive Summary's own
  acceptance criterion ("240 virtual NICs total") is authoritative over
  an illustrative snippet elsewhere showing VMs with fewer interfaces.
- **OVN/libvirt binding**: VM interfaces use `type='bridge'` with a
  `virtualport type='openvswitch'` `interfaceid` that must equal the OVN
  logical port name (`services/networking.py` and `core/xml_render.py`
  agree on this naming) — a plain bridge/VLAN interface, as sketched
  illustratively in the source doc, would not by itself give OVN logical-
  switch isolation between missions.
- **Deployment-scoped naming**: OVN switches/routers/ports are named
  `<mission>-<mission_id>-<network>` / `<mission>-<mission_id>-router` /
  `<mission>-<mission_id>-<vm>-<network>` — scoped by the unique
  `mission_id`, not just the human-readable mission name, so multiple
  concurrent *deployments of the identical mission definition* get
  genuinely separate OVN objects, not just distinguishable-looking names
  that would otherwise collide (`may_exist=True` would silently reuse the
  first deployment's switch for the second). See `CODE_REVIEW.md` §4.1
  for the full story of why this matters and how it was caught.
- **Management service SSH access**: the management service reaches every
  compute host's libvirt socket over SSH as `config/hosts.yaml`'s
  `management_ssh_user` (a dedicated, unprivileged service account with
  `libvirt` group membership) — not root, since STIG-hardened hosts
  commonly disable direct root SSH login. See `CODE_REVIEW.md` §4.1 and
  §6 for the account/group requirements this implies.
- **`DELETE /missions/{id}`** needs the original mission spec to know what
  to tear down; the in-memory store retains it from the original `POST`.
- **Cross-deployment resource contention is checked, not just per-mission
  capacity**: `POST /missions` validates a mission's placement against
  total host capacity (`core/placement.py:validate_placement`) AND
  atomically reserves its MAC prefix and specific GPU device slices
  against every other currently-active deployment
  (`core/state.py:MissionStore.register_deployment`) -- so two
  deployments that each look individually feasible, but together would
  oversubscribe the cluster's actual free MAC-prefix space or GPU
  slices, correctly get a `409 Conflict` on the second one rather than
  both succeeding and colliding later (originally an opaque libvirt/mdev
  error at define-VM time, for the GPU case).
- **Mission state persists across a management-service restart**, closing
  what was originally a known gap here. `core/state.py`'s MissionStore
  writes through to a SQLite database (stdlib `sqlite3` -- no new
  dependency, fully offline) whenever `MISSION_DB_PATH` is set (see
  `management/mission-management.service`, which sets it for a real
  deployment; unset, behavior is unchanged from before -- in-memory
  only). On startup, the database is reloaded BEFORE the API starts
  accepting requests, and `services/reconciliation.py` additionally scans
  every host's actual live libvirt domains and compares them against
  that reloaded state -- catching drift a database alone can't (a VM
  deleted directly via `virsh`, a management-service instance pointed at
  an already-provisioned cluster with no prior database at all). VM ->
  mission attribution for this scan works by reading a `<metadata>` block
  embedded in every VM's domain XML at deploy time (see
  `core/xml_render.py`), not by guessing from naming conventions, so a
  live VM can always be traced back to its mission even without a
  database record. **What reconciliation can't fully recover**: for a
  mission whose database record is missing entirely, only what a live
  domain's own XML exposes (VM names, actual MACs, GPU mdev UUIDs) is
  recoverable -- the original `networks:` VLAN mapping, `image_revision`
  pinning, and `file_version` are not written into a domain's XML and
  aren't recoverable this way; such a mission is reconstructed with
  `spec=None`, which is enough to know it exists and correctly free/hold
  its MAC prefix and GPU reservations, but not enough to redeploy or
  fully re-validate against acceptance criteria without the operator
  re-supplying the original mission file. Full multi-node HA (a
  clustered/replicated database, leader election for the management
  service itself) remains future work, as the design doc scopes it.
- **A failed deployment is automatically rolled back**, closing what was
  originally a known gap here. On any failure, `workers/deploy.py` now
  logs the error (via `core/logging_setup.py`, surfaced in the service's
  own console/journal output, not just queryable through the API) and
  tears down everything that attempt had already created -- VMs, then
  OVN networking, then runtime storage -- using the same idempotent
  teardown functions `DELETE /missions/{id}` uses, so it's safe to call
  regardless of which of the four steps the original failure happened
  at. If rollback fully succeeds, the mission moves to a distinct
  `RolledBack` state (not conflated with an operator-requested
  `Destroyed`) and frees its MAC prefix/GPU reservations, so the exact
  same mission can be resubmitted immediately with no leftover
  contention. If rollback itself hits an error, the mission is
  deliberately left in `Error` with its reservations still held, rather
  than freeing them while real leftover resources might still exist on
  some host -- that case needs a human to look at it.
