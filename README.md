# Linux-Native Virtualized Compute Cluster — Prototype

A working prototype implementation of the two-deliverable design described
in `Linux-Native_Virtualized_Compute_Cluster_Prototype.docx` and its
`Executive_Summary.docx`: replacing a VMware-based compute cluster with a
RHEL-native stack (KVM/libvirt, OVS/OVN, Ceph RBD) and automating it
end-to-end.

- **Deliverable A** (`bootstrap/`) — turns a fresh RHEL 9 server into a
  configured compute node.
- **Deliverable B** (`management/`) — a FastAPI service that provisions
  declarative "missions" (sets of VMs with networks, storage, and
  placement) across the cluster.
- **Proof of concept** (`management/mission_defs/mission_alpha.yaml`) — the
  40-VM mission from the Executive Summary: 10 persistent linked-clone
  VMs + 30 diskless PXE VMs, 6 NICs each (240 NICs total), 7 with GPU
  passthrough.

## Read this first: MAC addresses are an operator input, not generated

**Per operator confirmation, the guest software running inside mission
VMs has MAC addresses hardcoded into its licensing/configuration.** This
system therefore does **not** invent MAC addresses for real deployments —
every VM's `macs:` entry in a mission YAML is a required, explicit,
operator-supplied value that is used exactly as written.

`management/mission_defs/mission_alpha.yaml` has all 240 addresses filled
in already, but they are **arbitrary placeholders** (sequentially
numbered under the `52:54:00` QEMU/KVM OUI) generated by
`tools/generate_mission.py` purely so the file is complete and ready to
exercise end-to-end. **Replace them with your actual required addresses
before deploying against real hardware or licensed images.**

`core/macs.py` still contains a deterministic MAC generator, but it is a
*fallback only* for a VM whose mission entry omits `macs:` — it must never
be relied on for a VM whose guest software is MAC-locked. See that file's
docstring for the full rationale, and `core/macs.py`'s test suite
(`management/tests/test_macs.py`) for what guarantees it does and doesn't
provide (deterministic, collision-free up to 256 VMs/mission — but still
not a substitute for a real required address).

  modules/                   packages, libvirt_checks, networking, storage, gpu, cockpit, validation, util

management/                 Deliverable B: mission management service
  api/                       FastAPI app, routes, Pydantic models

  clients/                   thin wrappers: libvirt_client, ovn_client, ceph_client, nm_client
  services/                  compute, networking, storage, missions, validation
  workers/                   deploy.py, teardown.py (the background task workflow)
  templates/vm.xml.j2        the libvirt domain XML template
  inventory/                 hosts.yaml, networks.yaml, cluster.yaml (OVN/Ceph connection info)

## Architecture: why `management/core/` exists

The design doc specifies Pydantic models and a FastAPI app for the
management service. This build environment has **no network egress**, so
`fastapi`, `pydantic`, `ovsdbapp`, `python3-libvirt`, `python3-rados`, and
`python3-rbd` could not be installed or exercised here (see "What was and
wasn't executed," below).

Rather than leave the hardest, most bespoke logic in this project
untested, it's factored into `management/core/` as plain dataclasses and
pure functions with **zero dependency on fastapi, pydantic, or any of the
infrastructure client libraries** — only the standard library, PyYAML,
and Jinja2, all of which *are* available here. `management/api/models.py`
defines the Pydantic schemas the design doc calls for and converts to/from
these dataclasses at the API boundary, so a real deployment (with
`requirements.txt` installed) behaves exactly as specified, while every
non-trivial algorithm underneath it — MAC handling, capacity/placement
validation, libvirt XML generation, mission state transitions — is
unit-tested right now, in this repository, without any of those packages.

`management/clients/*.py` (libvirt/OVN/Ceph/NetworkManager wrappers) use
guarded imports (`try: import libvirt / except ImportError: libvirt =
None`) so the codebase imports cleanly even where those packages aren't
present, and raise one clear, actionable error if you call into them
without the real library installed. On a bootstrapped RHEL host, they're
installed by `bootstrap/modules/packages.py` and this guard never
triggers.

## What was and wasn't executed in this build environment

This project was built with no network access and none of
qemu-kvm/libvirt/OVS/OVN/Ceph/RHEL available — only Python 3.12, PyYAML,
and Jinja2. Here's exactly what that did and didn't allow:

**Executed and verified here, with real output shown during development:**
- `bootstrap.py`'s full orchestration in `--dry-run` mode, and its
  `--check-only` validation path against this (non-RHEL) sandbox, proving
  every module handles a missing/not-yet-bootstrapped host cleanly instead
  of crashing.
- 15 unit tests for `bootstrap/modules/*` (package diffing, IOMMU
  kernel-arg idempotency, validation aggregation, command execution and
  its failure modes).
- 77 unit/pipeline tests for `management/`, including:
  - Every domain-model validation rule in `core/types.py`.
  - `core/macs.py`'s collision-free VM indexing (including a regression
    test reproducing the exact bug this project hit: a 1-byte hash-based
    scheme collided once actually run against 40 VMs).
  - `core/placement.py`'s capacity validation and reference bin-packer.
  - `core/xml_render.py` rendering real libvirt domain XML for every VM
    shape (linked-clone, PXE, GPU, both storage backends) and parsing it
    back with `xml.etree.ElementTree` to confirm exact NIC count, MAC
    values, disk presence/absence, GPU hostdev presence/absence, and
    CPU/memory — i.e., directly checking the acceptance-criteria table.
  - The full pipeline against the *actual* generated 40-VM mission file:
    parse → placement validation → MAC resolution → XML rendering for
    all 40 VMs, confirming 240 total NICs, 7 GPU VMs only on GPU-capable
    hosts, and zero MAC duplicates.
  - `workers/deploy.py` / `workers/teardown.py`'s orchestration control
    flow (step ordering, GPU PCI allocation, error propagation, mission
    state transitions), with the services layer mocked out.
  - That `clients/*.py` import cleanly and fail with a clear, actionable
    error (not a crash) when the real libvirt/ovsdbapp/rados libraries
    aren't present.

**Written to spec but NOT executable here (no network, no real
infrastructure):**
- `management/api/*.py` (FastAPI routes and Pydantic models) — fastapi/
  pydantic/httpx aren't installable without network access. This code is
  a thin, well-trodden CRUD+background-task wrapper around the
  already-tested `core`/`services` logic; the risk surface it adds is
  low, but it has not been run.
- Any real call into `clients/libvirt_client.py`, `clients/ovn_client.py`,
  or `clients/ceph_client.py` — these need a real hypervisor, a real OVN
  Northbound DB, and a real Ceph cluster respectively. `ovn_client.py`'s
  `connect()` in particular follows the standard `ovsdbapp` IDL-connection
  pattern but its exact constructor signature has shifted across
  `ovsdbapp` releases — validate it against the pinned version in
  `requirements.txt` before relying on it.
- The shell scripts under `bootstrap/scripts/` and
  `bootstrap/tests/test_bootstrap.sh` — these are written for and must
  run on a real (or freshly kickstarted) RHEL host.
- GPU passthrough, PXE network boot, live migration, and STIG
  compliance scoring — all inherently require real hardware.

If you want to verify any of the "written to spec" pieces yourself: `pip
install -r requirements.txt` in a networked environment, then `pytest
management/tests` (all 77 tests are plain `unittest.TestCase`s and run
under pytest too) plus `uvicorn api.app:app --reload` from `management/`
to bring up the API against your own inventory.

## Prerequisites (real deployment)

- RHEL 9 hosts with VT-d/AMD-Vi enabled in BIOS for any host running GPU
  VMs.
- A Ceph cluster reachable from every compute host (or set
  `storage_backend: local_qcow2` per host to use the qcow2-backing-file
  fallback instead).
- A place to run `ovn-northd` and the OVN Northbound/Southbound DBs
  (`bootstrap/config/hosts.yaml`'s `ovn_central` — one of the compute
  hosts works for a prototype).
- Golden VM images (STIG-hardened RHEL, per the design doc) as QCOW2,
  either on a Ceph pool or under `/var/lib/libvirt/images/golden/`.

## Quickstart

```bash
# 1. Bootstrap each RHEL host (idempotent, safe to re-run)
sudo ./bootstrap/bootstrap.py --host compute01 --config-dir bootstrap/config
sudo ./bootstrap/bootstrap.py --host compute02 --config-dir bootstrap/config
# ...compute03, compute04

# 2. Install the management service's dependencies (in a venv, on a host
#    that can reach every compute node + the OVN NB DB + Ceph)
cd management
python3 -m venv venv && source venv/bin/activate
pip install -r ../requirements.txt

# 3. Review management/mission_defs/mission_alpha.yaml -- especially its
#    macs: section (see the callout at the top of this README) -- then
#    start the API
uvicorn api.app:app --host 0.0.0.0 --port 8000

# 4. Submit the mission
curl -X POST http://localhost:8000/missions \
    -H 'Content-Type: application/json' \
    -d @mission_defs/mission_alpha.yaml   # or convert to JSON first

# 5. Poll status
curl http://localhost:8000/missions/<mission_id>

# 6. Re-check acceptance criteria any time later
python3 ../tools/validate_deployment.py --mission-id <mission_id>

# 7. Tear down
curl -X DELETE http://localhost:8000/missions/<mission_id>
```

To regenerate `mission_alpha.yaml` (e.g. after changing
`management/inventory/hosts.yaml`'s capacity):
```bash
python3 tools/generate_mission.py
```
This rewrites the `vms:`/`placement:`/`macs:` sections from scratch —
re-apply any manual MAC edits you'd made afterward.

## Design choices and deviations worth knowing about

- **GPU host capacity**: the source doc's own illustrative host table
  only has 4 total GPU slots (2+2 across 4 hosts) — not enough for the
  scenario's 7 GPU VMs. `management/inventory/hosts.yaml` (and
  `bootstrap/config/hosts.yaml`) bump compute01/compute03 to 4 GPUs each.
  Confirm actual GPU counts/PCI addresses against your real hardware.
- **Every VM gets all 6 networks**: the Executive Summary's own
  acceptance criterion ("240 virtual NICs total") is authoritative over
  an illustrative snippet elsewhere showing VMs with fewer interfaces.
- **OVN/libvirt binding**: VM interfaces use `type='bridge'` with a
  `virtualport type='openvswitch'` `interfaceid` that must equal the OVN
  logical port name (`services/networking.py` and `core/xml_render.py`
  agree on this naming) — a plain bridge/VLAN interface, as sketched
  illustratively in the source doc, would not by itself give OVN logical-
  switch isolation between missions.
- **Mission-scoped naming**: OVN switches/routers/ports are named
  `<mission>-<network>` / `<mission>-router` / `<mission>-<vm>-<network>`
  so multiple missions can safely coexist on one OVN Northbound DB even if
  they reuse generic network/VM names.
- **`DELETE /missions/{id}`** needs the original mission spec to know what
  to tear down; the in-memory store retains it from the original `POST`.
- **Known gap**: mission state is in-memory and single-process, per the
  design doc's own scoping of HA as future work. A restart of the
  management service loses in-flight mission status (not the VMs
  themselves, which keep running under libvirt).
- **Known gap**: on a define-VM failure partway through a mission, VMs
  defined before the failure are left running (no automatic rollback) —
  the design doc explicitly scopes rollback as future work.

## Testing

```bash
# Bootstrap module tests (stdlib unittest, no real RHEL host needed)
python3 -m unittest discover -s bootstrap/tests -p 'test_*.py' -v

# Management service tests (stdlib unittest; also runs fine under pytest
# once installed)
python3 -m unittest discover -s management/tests -p 'test_*.py' -v
```

Both suites pass in this build environment (92 tests total: 15 bootstrap
+ 77 management). See "What was and wasn't executed" above for what's
covered and what still needs a real cluster to exercise.
